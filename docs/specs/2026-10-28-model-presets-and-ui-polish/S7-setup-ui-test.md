# S7 · 设置向导 UI 级测试：真子进程 + 管道喂键 + 假端点

> 父级：`../00-contract.md`　｜　契约条款：C8 的 UI 级延伸 + C13　｜　状态：已实现

## 为什么要单开一套

用户原话：「完善一下 UI 测试脚本，能模拟这种情况的发生，尽量把 bug 发现在 UI 测试阶段。」
随后给出交互规范：设置模型先等用户把 baseUrl / 模型 / key 补充完整，确认后再测连通性；
不可用可重设；通过后有旧配置要提示是否覆盖。

`test_setup.py` 是函数级：直接调 `step_embedding()`、桩掉 `probe_embedding`。401 事故
发生在真实按键流里（设置 → 选当前项 → 按 N → 探针发请求 → 401），函数级桩测一步都
复现不了。四条铁律第 4 条说的就是这种形态：**真 CLI 子进程 + 管道喂键**。

## 形态（不桩任何产品代码，铁律 2）

1. 起两台本地 HTTP 假 OpenAI 端点（各自只认自己签发的 key，别家 key 一律 401）
2. 真子进程跑 `hy-mem setup --step embedding/llm`，stdin 管道喂按键（非 TTY 自动降级编号菜单）
3. 断言退出码 / 输出文案 / config.json 最终形态 / **假端点看到的 Authorization 头**

假端点只绑 127.0.0.1 随机端口；不打真云厂商、不花真钱、可复现。
「旧 key 打新端点 → 401」在假端点上真实发生，而不是桩出一个 401。

## 首跑战果（红→绿三连）

| # | bug | 场景 | 修法 |
| --- | --- | --- | --- |
| 1 | 自定义分支 `same_endpoint` 写死 `True` → 换 baseUrl 静默继承旧 key，探针拿旧 key 打新端点 | D / E3 红 | 按刚填的新 baseUrl 对旧值计算（`custom_same`），注释写明事故日期 |
| 2 | 当前配置是自定义端点时默认光标落第 1 个预设 → 用户回车想「保持现状」实际秒变跨端点被追问 key | B 红 | `cur=-1` 且已有 baseUrl 时光标落「自定义」项（对齐 step_llm 既有行为） |
| 3 | `ask_secret` 无 default 时空回车放行空串 → apiKey=""+keyEnv=约定变量 → resolve 回落拿旧环境变量的 key | C 红 | 空回车当场重问（「密钥不能为空」），不发注定失败的请求 |

三个 bug 全在「第二次配置」家族——正是 401 事故的同族路径。

## 场景（25 项）

| 场景 | 验证点 |
| --- | --- |
| A 首次设置 | config 不存在时先 `_fill_from_env` 预填；走通自定义流；手填 key 落 apiKey；预填被覆盖时弹「覆盖旧配置」 |
| B 二次选当前项 | 三件套确认明示「环境变量 $MEMORY_EMBEDDER_API_KEY」；继承不落盘；无差异不问覆盖 |
| C 二次自定义跨端点 | 旧端点零请求；新端点只见新 key；旧 key 从未出现；baseUrl 已切换；覆盖提示出现 |
| D 二次换预设端点 | 明确告知「旧密钥不能复用」；EOF 中止后 config 一个字节未动 |
| E LLM 同型 | B/C 的 step_llm 版本（三件套确认、旧 key 不打新端点、手填落 apiKey） |

## 与 C13（设置四段式）的对应

C13 四段：①信息补齐确认（`_confirm_credentials`：三件套摆出来、可换 key、信息不齐
不发探针、防死循环兜底 Aborted）②信息完整才测连通性 ③不可用可重设（既有 retry/save/abort）
④有差异先摆旧→新对比再问「覆盖旧配置？」（`_credential_diff`）。

场景 B/C/E1 验证①②④；探针失败菜单（③）在产品层已有，A 场景的维度变更选择覆盖了它的
一个真实实例。

## 踩坑

- 首次设置的按键流比预期多两行：预填让默认光标落百炼（按 4 才是自定义）、维度变更会
  追加「重建/先不重建/放弃」三选一——按键流必须按真实输出逐步校准，猜必错。
- 函数级套件的 `tui.confirm=False` 桩会撞上 C13 的确认环节死循环（确认→换 key→再确认）；
  修法是产品侧兜底 Aborted + 测试桩改 True。这是 C13 落地后所有旧桩测试的通用注意项。
